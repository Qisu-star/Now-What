## 1. 周期性事务（重复安排）

| 项 | 内容 |
| --- | --- |
| 记录日期 | 2026-11-08 |
| 来源 | 用户提出 |
| 优先级 | 后续迭代（P1，不阻塞 v1） |
| 状态 | 待评估 |

### 背景

现有模型里，每个事务都是一次性的：安排好、到期、归档。但学生一学期会有每周固定的课程，普通人会有每周固定的运动、减肥、学习计划。这类事务持续数周甚至数月，如果每周都手动创建、手动拖进日程表，既麻烦又容易漏。

### 目标

一次定义重复规则，系统自动把后续各周的安排生成到日程表里；同时允许对某一次单独调整或跳过，不必每次重新建事务。

### 初步设想（待细化）

1. **重复规则**挂在事务上：
   - 频率：每周、每两周、每 N 周；
   - 周几：单选或多选（如每周二、周四）；
   - 时段：开始时间与时长（如 14:00–16:00）；
   - 生效范围：起始日期 + 结束日期（或重复次数）。
2. **展开方式**：进入周表 / 月表时，按规则展开成计划时段，渲染与普通安排一致。
3. **单次例外**：
   - 跳过某一次（放假、调休）；
   - 单次改时间或改时长；
   - 单次取消不影响整个系列。
4. **编辑规则**：修改「之后的所有」或「仅这一次」，两者要能区分。
5. **展示**：列表与详情页显示「每周二」标签；日程卡片可以加一个小循环图标，区分重复生成与手动安排。

### 需要先想清楚的问题

- **周期与截止时间的关系**：现在事务有独立的「截止时间」，重复事务的截止时间是指整个系列的结束，还是每一期各自的截止？
- **归档粒度**：每一次完成后单独归档，还是整个系列一起归档？如果每次单独归档，一个系列会变成很多条历史记录。
- **冲突处理**：某一次的时间被别的事务占用时，是跳过、顺延，还是提醒用户处理？
- **修改规则的历史影响**：改规则时，已经过去的安排要不要动？未来的已单独调整过的安排要不要保留？
- **例外日期**：是否需要支持节假日批量跳过。
- **导出与统计**：导出的表格里重复事务展开成多行还是标注规则。

### 对现有设计的影响

- 数据模型：事务上增加重复规则（如 `recurrence`），计划时段增加来源标记（自动生成 / 手动调整 / 跳过），现有 `source` 字段可以扩展。
- 渲染：周表、月表逻辑不变，只是数据量变大，需考虑一次展开几周。
- 详情页：增加规则编辑器与「本次 / 全部」的编辑范围选择。
- 与「同一时段只安排一个事务」：展开时必然要做冲突检测，展开策略要先定。

### 与现有扩展项的关系

需求文档 v1.2 已列出的扩展项是子事务、日程导入、搜索筛选；周期性事务与它们并列，属于同一层的「后续能力」。
