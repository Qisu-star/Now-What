# ADR：时间与时区的存储方式

> 编号：ADR-002
> 状态：已采纳
> 日期：2026-11-08
> 关联 Spec：[003 日程表视图](../specs/003-calendar-views.md)、[004 排期与拖拽](../specs/004-scheduling.md)

## 背景

应用里有两类时间，语义不同：

- **事务周期**：一个绝对时刻（截止到某天某时），像闹钟一样指向时间轴上的一个点。
- **计划时段**：用户把它放在日历的哪一天、哪一段时间，本质是「本地墙上的位置」。

如果两者都用同一种方式存，要么查询某天时要反复换算，要么跨时区时含义错乱。本期是单机单用户、单一时区，但代码结构要经得起以后加时区。

## 决策

- **事务周期用 UTC 存储**：`start_at` / `end_at` 为 ISO 8601 UTC 字符串，对应绝对时刻。
- **计划时段用墙上时间存储**：`day`（本地日期 `YYYY-MM-DD`）+ `start_minute` / `end_minute`（0–1440 的整数），不存 UTC。日历上「周二 14:00」就是周二 14:00，与时刻换算无关。
- **时钟可注入**：业务代码通过一个 `Clock` 接口取当前时间，不在逻辑里直接 `new Date()`；测试传固定时间，生产用系统时钟。
- **单时区假设**：本期服务端与用户都在 Asia/Shanghai，不处理夏令时；「今天」以服务端本地时区的日期为准。
- **跨天安排**：允许一条计划时段跨过 0 点，但在周表/日表中按天切分渲染；不拆成两条记录。

> 本条修订 `architecture.md` 第 6 节中「placements 以 UTC 存储」的表述，以本条为准。

## 原因

- 计划时段是日历上的位置，用日期 + 分钟表示最直接，按天查询不需要时区换算，也不受时区变化影响。
- 事务周期是「什么时候之前必须做完」，用绝对时刻更符合语义。
- 可注入时钟让「逾期」「今天」「自动落位」这些逻辑可被稳定测试。
- 明确单时区假设，避免在没有需求的情况下引入时区库和复杂度。

## 后果

- 若将来支持跨时区用户，计划时段需要额外记录创建时的时区，届时再引入 `timezone` 字段与迁移；本期不预留。
- 服务端和前端都必须按同一套规则把「日期 + 分钟」渲染成时间，规则放在 shared。
- 数据库查询按 `day` 建索引即可，不需要对计划时段做时间范围换算。

## 不采用

- **计划时段也存 UTC**：每次渲染与查询都要换算，跨天切分更麻烦，收益为零。
- **全部存本地时间字符串**：比较、排序、跨天计算都要解析字符串，容易出错。
- **直接使用 `new Date()`**：测试无法固定时间，逾期与自动落位的用例会随运行时刻漂移。
- **现在就引入完整时区支持**：没有多时区需求，先按单时区实现并在文档中声明边界。
