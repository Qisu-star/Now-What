# ADR：OpenAPI 由 zod schema 生成，而非手写

> 编号：ADR-004
> 状态：已采纳
> 日期：2026-11-08
> 关联 Spec：[001 事务管理](../specs/001-task-management.md)、[004 排期与拖拽](../specs/004-scheduling.md)

## 背景

前后端需要一份共同认可的接口契约。常见做法有两种：手写 `openapi.yaml` 作为事实来源，或者让后端代码生成契约。手写的优点是前后端可以并行开工；缺点是实现一改、文档不跟着改，几周后就不可信。

本项目是单人开发、接口数量有限（约 11 个），后端与前端由同一人维护，手写契约的并行收益很小，漂移的代价却很大。

## 决策

- **以 `packages/shared` 中的 zod schema 为唯一事实来源**，它同时承担三件事：后端请求/响应校验、前端表单校验、OpenAPI 文档生成。
- 后端用 `fastify-type-provider-zod` 注册路由，`@fastify/swagger` 在启动时产出 `openapi.json`。
- 前端用 `openapi-typescript` 从 `openapi.json` 生成类型，用 `openapi-fetch` 发起请求。
- 契约版本前缀 `/api/v1`；破坏性变更升版本。
- 生成物（`openapi.json`、前端类型文件）提交到仓库，并在 CI 中重新生成后比对，出现差异即失败。

## 原因

- 一份 schema 同时服务校验与文档，不存在「文档写的和代码做的不一致」。
- 前端类型由契约生成，字段改名会在编译期报错，而不是运行时才发现。
- 生成物入库，评审时能看到接口变化，也避免每次拉代码都要先生成。
- 相比 tRPC，OpenAPI 更通用，将来接入其他客户端或第三方时不需要重做。

## 后果

- 新增接口的顺序固定：先改 shared schema，再写路由，再生成契约与前端类型。
- `openapi.json` 每次变更都会出现在 diff 里，提交信息需要说明契约变化。
- 生成物与手工代码要分开存放，避免生成时覆盖业务文件。
- 需要一条 CI 检查：重新生成后 `git diff --exit-code`。

## 不采用

- **手写 `openapi.yaml` 再分别实现**：单人体量下并行收益小于漂移成本。
- **tRPC / GraphQL**：契约不通用，且本项目不需要按字段裁剪。
- **只靠 TypeScript 类型共享、不产出 OpenAPI**：运行时没有校验，也无法生成文档。
