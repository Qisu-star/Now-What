# ADR：服务端是唯一真相，领域规则在 shared 中共用

> 编号：ADR-001
> 状态：已采纳
> 日期：2026-11-08
> 关联 Spec：[004 排期与拖拽](../specs/004-scheduling.md)、[001 事务管理](../specs/001-task-management.md)

## 背景

排期涉及大量时间计算：自动落位、重叠判定、吸附、命中判定。这些规则如果前端写一份、后端写一份，迟早会漂移，表现为「界面上能放，提交却被拒绝」或者反过来。原型阶段已经在 `domain/slots.ts`、`domain/hit.ts`、`domain/form.ts` 里写过一套纯函数并配了单元测试，值是现成的。

同时，本期虽然是单用户本地应用，但数据必须落库、刷新后不丢，因此需要一个明确的写入出口。

## 决策

- **数据写入只经过服务端 API**：前端不直接读写数据库，也不维护第二份持久化状态。
- **领域规则下沉到 `packages/shared`**：时间段运算、重叠判定、自动落位、吸附、命中判定、表单校验都以无 DOM 依赖的纯函数实现，前后端引用同一份代码。
- **前端只做预演**：拖拽过程中用 shared 的函数实时判断「能不能放」，但最终结果以服务端返回为准；服务端判定冲突时返回 409，前端回滚到操作前状态并提示。
- **shared 自带单元测试**：每条规则至少一个用例，测试与实现同仓，随 `pnpm check` 执行。
- **服务端不复用前端组件**：shared 只包含与运行时无关的纯逻辑和 schema，不引入 Vue 或浏览器 API。

## 原因

- 冲突检测必须有一个仲裁者，否则并发写入时无法保证「同一时段只有一张卡片」。
- 规则集中在一处，改一次两端同时生效；单元测试只写一份。
- 前端预演保证交互跟手，服务端裁决保证数据正确，两者各司其职。
- 纯函数易于测试，也便于将来移植到其他端。

## 后果

- 每次拖拽或拉伸都会产生一次写请求；若交互频繁，需要做防抖与乐观更新。
- shared 的改动会同时影响前后端，需要保持在语义层面的兼容。
- 服务端必须提供可注入的时钟，否则测试无法稳定复现「今天」。
- 原型中的 `slots.ts`、`hit.ts`、`form.ts` 及对应测试可以直接迁移，减少重复实现。

## 不采用

- **只在前端校验**：刷新或换设备后数据可能不一致，且无法防止绕过界面的写入。
- **前后端各写一套规则**：短期快，长期一定会出现两侧判断不一致。
- **把规则写进数据库约束**：数据库能做唯一性和区间排除，但做不了「向更早找空位」这类业务顺序，维护成本更高。
- **引入离线写队列**：本期是单机单用户，先不做同步冲突合并。
