# ADR：本期范围裁剪，附件与导出延后

> 编号：ADR-003
> 状态：已采纳
> 日期：2026-11-08
> 关联 Spec：[006 附件与导出](../specs/006-attachments-and-export.md)、[plan.md](../../plan.md)

## 背景

需求文档 v1.2 描述了完整的第一版：事务、列表、日程表、排期、归档、附件、导出、移动端适配、多标签页同步。这些能力的技术性质差别很大：附件涉及文件存储、预览与下载，导出涉及生成 xlsx / png，两者都是独立的子系统；而事务与排期是产品的核心闭环。

一次性全部推开，会让「能不能用」这个最基本的判断被推到很后面。

## 决策

把本期拆成三个阶段：

- **M0–M4：核心闭环**（事务、列表、日历、排期、归档）——本期交付目标。
- **M5：附件与导出**——核心闭环验收通过后再做，Spec 006 保持「延后」状态。
- **M6：移动端布局与多标签页同步**——同样后置。

判断标准：如果只能交付一件事，应该是「创建事务 → 排进日程 → 完成归档」这条链路可用且数据不丢。

## 原因

- 核心闭环验证的是产品假设；附件和导出是锦上添花，不改变主流程。
- 文件存储会引入目录管理、大小限制、清理策略；导出会引入字体、分页、截图兼容问题。两者都会显著拉长首次可用时间。
- 先做完核心闭环，能更早拿到真实使用反馈，避免在附件交互上做了大量返工。
- 三阶段拆分不影响数据模型：附件表结构可以在 M5 再加，不需要提前设计。

## 后果

- 需求文档 v1.2 中「事务附件」「日程导出」两节在 M5 之前不验收；详情页保留说明性占位。
- `specs/006` 保持「延后」，不阻塞 M0–M4 的验收。
- 归档弹窗中的「归档附件」字段本期只保留数据位，不做上传入口。
- 若用户强烈要求提前，可把 M5 中的单独一项（例如图片导出）提前，但不改变 M0–M4 的优先级。

## 不采用

- **一次做完所有功能**：首次可用时间被拉长，反馈来得太晚。
- **直接砍掉附件与导出**：需求明确要求，只是顺序问题，不是取舍问题。
- **先做导出再做排期**：导出依赖稳定的视图与数据模型，顺序反了会返工。
